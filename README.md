## Мета роботи
Практичне засвоєння методів проєктування та розробки програмного забезпечення з використанням об'єктно-орієнтованого програмування, архітектурних підходів (REST API, SOLID, GRASP) та GoF-шаблонів проєктування.

## Основні функції та вимоги системи (Варіант 10)

- [x] **Стрічка новин:** головна сторінка зі свіжими публікаціями, ієрархічні тематичні рубрики (політика, економіка, технології тощо), фільтрація та сортування (за датою, популярністю або персоналізовано).
- [x] **Персоналізація контенту:** налаштування улюблених категорій у профілі, персоналізована стрічка та рекомендації на основі вподобань і переглянутих статей.
- [x] **Профіль користувача:** збережені статті (закладки / читати пізніше), система коментування, вподобання (лайки) та історія переглядів.
- [x] **Система підписок:** розмежування рівнів доступу (безкоштовний перегляд публічних матеріалів / платна преміум-підписка з доступом до ексклюзивного контенту та керуванням станами підписки).
- [x] **Система сповіщень:** сповіщення про нові публікації улюблених авторів та щоденні дайджести через різні канали доставки (Email, Push тощо).
- [x] **Панель адміністратора / модератора:** керування публікаціями, ієрархією категорій, тарифними планами та користувачами (блокування/бан).

## Архітектура системи

Система побудована на засадах Clean / Layered Architecture із чітким розмежуванням відповідальності між шарами:

<img width="7128" height="3088" alt="image" src="https://github.com/user-attachments/assets/10d43cac-3978-415b-aae6-30789b88a797" />

- **Presentation Layer (Web UI):** Клієнтський інтерфейс для перегляду новин, кабінет автора для написання статей та панель адміністратора.
- **API Layer (RESTful API):** Контролери маршрутизації вхідних HTTP-запитів, валідація DTO, передача виконання у бізнес-логіку.
- **Business Logic Layer (Core Domain & Services):** Ядро системи. Тут інкапсульовані всі доменні сутності, бізнес-правила, життєві цикли та GoF-патерни.
- **Data Access Layer (Persistence):** Патерн Repository для абстрагування операцій над базою даних.

## Рольова модель (RBAC)

| Роль | Права та можливості в системі |
| :--- | :--- |
| **Гість** | Неавторизований доступ; читання базових публічних новин; перегляд прев'ю преміум-статей; реєстрація. |
| **Читач** | Особистий профіль; вибір улюблених категорій; збережені статті (закладки); коментування та лайки; оформлення та керування станом підписки; підписка на авторів. |
| **Журналіст** | Усі права читача + створення та редагування власних публікацій (зокрема преміум-матеріалів) через конструктор статей; перегляд розділу «Мої статті». |
| **Адміністратор** | Модерація публікацій і коментарів; керування ієрархією рубрик; керування тарифними планами; керування чорним списком користувачів (бан). |

## Принципи проєктування (SOLID & GRASP)

### Принципи SOLID
**S (Single Responsibility Principle):** Кожен клас має лише одну причину для зміни. Фабрика сповіщень відповідає за створення повідомлень для обраного каналу, сервіс дайджестів — за формування щоденних добірок, а репозиторій — за комунікацію з БД.

**O (Open/Closed Principle):** Модулі відкриті для розширення, але закриті для модифікації. Нові канали розсилки (Email, Push, Telegram) чи стратегії формування стрічки додаються створенням нових класів без редагування базового коду.

**L (Liskov Substitution Principle):** Будь-яка реалізація стратегії вибірки (`IFeedStrategy`), стану підписки (`ISubscriptionState`) або вузла категорій (`CategoryComponent`) підставляється замість базового інтерфейсу без порушення коректності роботи клієнтського коду.

**I (Interface Segregation Principle):** Інтерфейси розділені за ролями клієнтів. Читач взаємодіє з інтерфейсами споживання новин та підписок, а методи створення й публікації статей винесені в окремі компоненти для авторів.

**D (Dependency Inversion Principle):** Верхні рівні бізнес-логіки залежать від абстракцій (інтерфейсів репозиторіїв, фабрик та стратегій), а не від конкретних реалізацій інфраструктури.

---

### Принципи GRASP
**Information Expert:** Інформаційним експертом доступності преміум-контенту є сутність `Subscription` (через свій поточний стан `ISubscriptionState` та тариф `SubscriptionPlan`), а взаємодій читача зі статтями — `ArticleInteraction` та `User`.

**Controller:** Обробку вхідних запитів ініціюють REST-контролери, які не містять важкої бізнес-логіки, а координують виклики фасадів і сервісів.

**Low Coupling & High Cohesion:** Досягнуто слабку зв'язаність компонентів через інтерфейси та високу функціональну зв'язаність кожного окремого сервісу навколо власної предметної області.

### Каталог патернів проєктування GoF

| Патерн | Категорія | Місце в системі | Вирішувана проблема / Опис реалізації |
| :--- | :--- | :--- | :--- |
| **Builder** | Породжувальний | `ArticleBuilder` (`IArticleBuilder`) | Дозволяє покроково конструювати складний об'єкт статті: додавати заголовок, контент, медіа-вкладення, теги, прив'язку до категорії та статус ексклюзивності (`isPremium`). |
| **Factory Method** | Породжувальний | `NotificationFactory` (`INotification`) | Делегує створення конкретних об'єктів сповіщень підкласам (`EmailNotificationFactory`, `PushNotificationFactory` тощо) для різних каналів доставки новин і дайджестів. |
| **Facade** | Структурний | `ArticlePublishingFacade` | Надає єдиний спрощений інтерфейс для комплексного процесу публікації статті: збереження в БД та автоматичне сповіщення підписників автора. |
| **Composite** | Структурний | `CategoryComponent` (`Category`, `CategoryGroup`) | Формує деревоподібну ієрархію рубрик новин. Дозволяє уніфіковано отримувати статті як для окремих підрубрик («Футбол»), так і для батьківських категорій («Спорт» разом із дочірніми вузлами). |
| **Observer** | Поведінковий | `IAuthorObserver` / `ArticlePublisher` | Реалізує механізм підписки читачів на улюблених авторів. Подія публікації нової статті автоматично сповіщає всіх підписаних слухачів. |
| **Strategy** | Поведінковий | `IFeedStrategy` (`NewsFeedService`) | Забезпечує динамічну зміну алгоритму формування стрічки новин: за хронологією (`ChronologicalFeedStrategy`), за популярністю (`PopularFeedStrategy`) або персоналізовано (`PersonalizedFeedStrategy`). |
| **State** | Поведінковий | `ISubscriptionState` (`Subscription`) | Інкапсулює поведінку підписки залежно від її поточного стану (`ActiveState`, `ExpiredState`, `CancelledState`), визначаючи права доступу до преміум-контенту без громіздких розгалужень `if/else`. |
