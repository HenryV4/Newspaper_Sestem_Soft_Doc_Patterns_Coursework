## Основні функції та вимоги системи (Варіант 10)

- [x] **Стрічка новин:** головна сторінка зі свіжими публікаціями, тематичні рубрики (політика, економіка, технології тощо), повнотекстовий пошук та фільтрація за датою/автором.
- [x] **Персоналізація контенту:** налаштування улюблених тем, персоналізована стрічка та рекомендації на основі вподобань/переглядів.
- [x] **Профіль користувача:** збережені статті (читати пізніше), система коментування, оцінки (лайки/дизлайки).
- [x] **Система підписок:** розмежування рівнів доступу (безкоштовний перегляд / платна преміум-підписка без реклами та з ексклюзивним контентом).
- [x] **Система сповіщень:** push-повідомлення про гарячі новини (*Breaking News*), підписка на дайджести та авторів.
- [x] **Панель адміністратора / модератора:** CRUD для публікацій, категорій, керування користувачами та аналітика.

## Архітектура системи

Система побудована на засадах Clean / Layered Architecture із чітким розмежуванням відповідальності між шарами:

<img width="7128" height="3088" alt="image" src="https://github.com/user-attachments/assets/10d43cac-3978-415b-aae6-30789b88a797" />

* Presentation Layer (Web UI): Клієнтський інтерфейс для перегляду новин, кабінет автора для написання статей та панель адміністратора.

* API Layer (RESTful API): Контролери маршрутизації вхідних HTTP-запитів, валідація DTO, передача виконання у бізнес-логіку.

* Business Logic Layer (Core Domain & Services): Ядро системи. Тут інкапсульовані всі доменні сутності, бізнес-правила, життєві цикли та GoF-патерни.

* Data Access Layer (Persistence): Патерн Repository для абстрагування операцій над базою даних.

| :--- | :--- |

## Принципи проєктування (SOLID & GRASP)

### Принципи SOLID
**S (Single Responsibility Principle):** Кожен клас має лише одну причину для зміни. Сервіс сповіщень займається транспортом повідомлень, процесор контенту — рендерингом тексту, а репозиторій — комунікацією з БД.

**O (Open/Closed Principle):** Модулі відкриті для розширення, але закриті для модифікації. Нові канали розсилки (Telegram, SMS) чи алгоритми рекомендацій додаються створенням нових класів без редагування базового коду.

**L (Liskov Substitution Principle):** Будь-яка реалізація стратегії вибірки або стану підписки підставляється замість базового інтерфейсу без порушення коректності роботи клієнтського коду.

**I (Interface Segregation Principle):** Інтерфейси розділені за ролями клієнтів. Читач взаємодіє з інтерфейсами споживання новин, а методи публікації винесені в окремі інтерфейси для авторів.

**D (Dependency Inversion Principle):** Верхні рівні бізнес-логіки залежать від абстракцій (інтерфейсів репозиторіїв та шлюзів), а не від конкретних реалізацій інфраструктури.

---

### Принципи GRASP
**Information Expert:** Інформаційним експертом рейтингу/лайків є сама сутність Article; статус доступності контенту визначає сутність User / Subscription.

**Controller:** Обробку запитів ініціюють REST-контролери, які не містять важкої логіки, а координують виклики фасадів і сервісів.

**Low Coupling & High Cohesion:** Досягнуто слабку зв'язаність компонентів через інтерфейси та високу функціональну зв'язаність кожного окремого сервісу навколо власної предметної області.

### Каталог патернів проєктування GoF

| Патерн | Категорія | Місце в системі | Вирішувана проблема / Опис реалізації |
| :--- | :--- | :--- | :--- |
| **Builder** | Породжувальний | `ArticleBuilder` | Дозволяє покроково конструювати складний об'єкт статті: комбінувати параграфи, медіа-вкладення, галереї, перелік тегів, рубрики та статус ексклюзивності (`isPremium`). |
| **Factory Method** | Породжувальний | `NotificationSender` | Делегує створення конкретних типів повідомлень: терміновий мобільний Push для Breaking News, Email-дайджест для щотижневої розсилки або системний івент. |
| **Decorator** | Структурний | `ArticleContentProcessor` | Динамічно нашаровує логіку обробки тексту: `AdBannerDecorator` інжектує блоки реклами для безкоштовного тарифу, а `PaywallDecorator` обрізає статтю для платних матеріалів. |
| **Facade** | Структурний | `ArticlePublishingFacade` | Надає єдиний спрощений інтерфейс для комплексної публікації: збереження в БД, індексація пошуковим рушієм, інвалідація кешу та тригер розсилки підписникам. |
| **Composite** | Структурний | `CategoryComponent` | Формує деревоподібну структуру рубрик новин. Дозволяє уніфіковано отримувати статті як для листових рубрик («Футбол»), так і для батьківських вузлів («Спорт» → включає всі дочірні матеріали). |
| **Adapter** | Структурний | `SanitizedTransactionAdapter` | Адаптує сирі дані зовнішніх платіжних систем до внутрішнього інтерфейсу адмін-панелі, маскуючи чутливі банківські реквізити (наприклад, картка перетворюється на `**** **** **** 1234`). |
| **Observer** | Поведінковий | `ArticlePublisher` / `Subscriber` | Реалізує підписку читачів на улюблених авторів або теми. Подія успішної публікації сповіщає всіх підписаних слухачів у фоновому режимі. |
| **Strategy** | Поведінковий | `RecommendationStrategy` | Забезпечує динамічну підміну алгоритму формування стрічки користувача: за хронологією, за популярністю (перегляди/лайки) або персоналізовано (на основі історії та тегів). |
| **State** | Поведінковий | `SubscriptionState` | Інкапсулює логіку стану облікового запису (`FreeTier`, `ActivePremium`, `Expired`). Позбавляє код складних розгалужень `if/else`, делегуючи стан безпосередньо об'єкту тарифу. |
| **Template Method** | Поведінковий | `DashboardService` | Задає інваріантний алгоритм збору даних для кабінету: отримання профілю → отримання ролевих метрик → формування сповіщень. Специфіка для журналіста чи адміна перевизначається в підкласах. |
| **Chain of Responsibility** | Поведінковий | `AccessValidationHandler` | Організовує конвеєр послідовної перевірки запиту до статті: Валідація сесії → Перевірка чорного списку (Ban check) → Перевірка прав ролі → Перевірка наявності преміум-доступу. |
